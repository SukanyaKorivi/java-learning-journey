Static methods: they never had a vtable entry to begin with. 
Static methods aren’t part of the instance method dispatch system at all — 
they belong to the class itself, not to any object’s polymorphic behavior. There’s nothing to “skip” — 
the vtable mechanism was never in play. This is why static “overriding” isn’t real overriding, 
it’s hiding: call it through a reference, and Java picks the method based on the declared type of the reference variable, 
completely ignoring the actual object’s runtime type.

super.method(): the method absolutely does have a vtable entry 
— it’s a normal instance method, fully polymorphic, fully part of the dynamic dispatch system for every other kind of call. 
super doesn’t mean “this method has no vtable entry” — it means “for this one call site, compile a direct reference (invokespecial) instead of consulting the vtable.” 
The vtable entry still exists and is still used by every other call to that method (e.g., a normal animalRef.makeSound() on a Dog object still goes through the vtable and gets Dog’s version).


they share a surface similarity (both resolved at compile time, not runtime), but the reason is different in each case — 
static methods are outside the dispatch system entirely, while super calls are inside the dispatch system but deliberately routed around it for that one call. 
That’s “fundamentally different,” not “the same mechanism.
